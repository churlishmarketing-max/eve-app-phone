## 2. KATANA in detail — the "edit a video into a trailer" example

**How it runs:** two halves, both documented in `OPERATIONS.md`:
- **The panel** — a UXP plugin (`.ccx`) that must be installed inside **Premiere Pro (Beta) 26.2.x** specifically. Stable Premiere 26.0 has no UXP host at all ("Host Application specified is not available" — confirmed in `CAPABILITY.md`). This is a hard environment requirement, not a preference.
- **The brain** — a Supabase edge function (`katana-brain`, project `iunfuunwhhcfgptiaavk`, same Supabase project KATANA and Churlish OS both live under) that holds the Anthropic key server-side and returns clip/kill/brief JSON. Panel↔brain auth is a static shared bearer token (`KATANA_TOKEN`); brain↔Anthropic key never touches the plugin.

**What it needs to actually cut something:**
1. Premiere Pro (Beta) open, with the target project and its master sequence active.
2. A transcript — either exported from Premiere's Text panel (SRT/TXT/CSV) or pulled directly from the active sequence via `Transcript.exportToJSON` (works, confirmed in the M0/M2 capability audit).
3. A human in the panel picking client + mode + hitting RUN, then reviewing result cards and hitting APPLY. Every run is logged to `KATANA/<run-id>/` next to the project (run.json, clip-sheet.md, editor-brief.md, katana.xml fallback) and is non-destructive — the master sequence is never touched; every mode either creates new sequences or a `_KATANA-CLEAN` duplicate.

**Could a desktop app hand it a job?** Not as built. The cutting itself (`premierepro` module calls — insert, trim, disable, ripple-remove, marker, clone, bin move) only exists inside Premiere's own JS runtime; there is no exposed local socket, file-watch, or queue table the panel polls. The brain endpoint alone is callable from outside (it's just HTTPS), but calling it only produces a *plan* — turning that into an actual cut still requires a human physically in Premiere clicking APPLY, or a future build task adding a poll-a-queue feature to the panel plus OS-level automation to drive Premiere. Today: zero automated trigger surface.

**Current status per its own docs:** Fully built through **M7 (package + install)** — `dist/`, `ccx/com.churlish.katana_premierepro.ccx`, and `OPERATIONS.md` (explicitly "the M7 deliverable") all exist. `CAPABILITY.md` shows **18 of 20 Premiere operations verified WORKS (0 absent)** as of the 2026-07-14/15 audits — the cut engine runs Tier A (full native auto-cut), with the FCPXML Tier-C fallback built regardless. It is a real, shipped internal tool, not a prototype — but it is **not listed in the Second Brain roster** yet (`references/roster.md` has no KATANA row; the README itself flagged this as an open assumption: "unclaimed in the Second Brain roster").

## 3. Churlish OS in detail

**What data it owns (Supabase, `schema.sql` + 24 numbered migration files under `supabase/`):** sprint targets/dates, deals/pipeline, weekly Friday-Five metrics, sys.log feed, founder/habits/goals/ops state, clients, invoices, proposals, booking, intake/onboarding forms, automations + automation rules, diagnostic funnel (Authority Diagnostic), fleet roster mirror, Crucible session notes, payments, Google Meet integration, offers catalog. This is the single real database behind Brandon's business numbers — not a mockup.

**Does it expose an API the desktop could read?** Yes, and it already exists for exactly this purpose: `app/api/eve/route.ts` is documented in its own comments as "EVE's door into the OS" — a bearer-token-gated (`EVE_OS_TOKEN`) tool-calling endpoint. `GET` lists available tools; `POST {tool, input, confirmed}` executes one. It already implements the RED-tier law server-side: `send_pending_email` and `draft_client_email` with `send_now` are refused with `confirmation_required` unless `confirmed:true` is set — independently of whatever the brain itself does, so a compromised or prompt-injected brain can't email a client through this door alone. There's also `app/api/fleet/roster` (GET/POST, different secret) that the Second Brain skill's "Update Protocol" already POSTs to, keeping the OS's fleet-manifest mirror in sync with `roster.md`.

**What "a local slice focused on Churlish Media" would actually mean:** Churlish OS is not a local program at all — it's a Vercel-hosted Next.js app over Supabase, with its own login and its own cron. The brain already reads/writes it wholesale through `/api/eve`. So a "local slice" cannot mean giving the desktop hub *new* access — that access already exists at the data layer. It can only mean: **a filtered view** — the desktop hub calling the same `/api/eve` tools (or reading Supabase directly) but rendering only the Churlish-Media-relevant subset (board, pipeline, clients, invoices) inside the hub's own UI, as a convenience surface, not a new integration. It would duplicate a subset of what a browser tab already shows. The one thing actually local about the "local slice" idea is presentation (a native panel in the hub instead of a browser tab) — not data or execution, both of which are already cloud-side.

## 4. Skills library

**Physically, on this machine:** `C:\Users\mrkin\.claude\skills` holds **5 skill folders**: `frontend-design`, `jimmy-olsen`, `mister-miracle`, `second-brain`, `ui-ux-pro-max`. Each is a folder with a `SKILL.md` (name + description frontmatter + instructions) and optional `references/`/`assets/` subfolders.

**But the fleet is bigger than that folder.** `second-brain`'s own roster (`references/roster.md`) tracks **49 units across 6 divisions**, tagged by location: `WS` (installed as a Claude skill in a workspace — i.e., lives as a skill definition Claude Code/Claude.ai loads, not necessarily on this filesystem) or `CC` (lives inside the Claude Code EVE fleet / brain project, e.g. Oracle, Pennyworth, Cyborg, Steele — these are prompted behaviors inside the brain's own code, not standalone skill files at all). KATANA doesn't even appear in the roster yet. Separately, this Claude Code session's own tool list shows dozens more skills available from plugin marketplaces (`anthropic-skills:*`, `small-business:*`, `marketing:*`, etc.) — those are plugin-provided, loaded by the harness, and are not files under `C:\Users\mrkin\.claude\skills` either. So "how many skills" has three different true answers depending on which layer you mean: **5 local files**, **49 roster-tracked units** (mixed WS/CC, mostly not local files), or **a much longer plugin-catalog list** available to any Claude Code session on this account.

**What "running a skill" means mechanically — it is not a program.** A skill is a Markdown file: a `description` (used for auto-trigger matching) plus instructions in prose. There is no `execute()`, no binary, no server. "Running" a skill means: a Claude model, mid-conversation, reads that file's text into its own context window and then follows the instructions itself, using whatever tools *that same model session* already has (Read/Write/Bash/etc., or MCP tools). Nothing happens without a live LLM turn in a live agent session paying for and producing that turn.

**What it would take for a desktop app to invoke one and get a result back:** there is no local skill-runner binary to shell out to. The only way to "invoke" one from the desktop hub is to start (or reuse) an actual Claude agent session — e.g. spawn a Claude Code process (`claude` CLI) with a prompt that names/triggers the skill, or send a message to a running EVE brain session that has that skill's instructions loaded — and then wait for that session to finish its turn(s) and read back whatever it wrote (a file, a chat reply, an artifact). The desktop app's own job list would be tracking *that agent session's* lifecycle (queued → running → produced X), not calling a skill "API." Skills that live purely as `CC` roster entries (Oracle, Pennyworth, Cyborg, etc.) already work exactly this way today, inside the brain — the desktop-side version of this is the same mechanism, pointed at the same brain, with a job card instead of a chat bubble.

## 5. Which stated wants genuinely require local execution vs. only feel local

**Genuinely local (can only happen on this machine, at least today):**
- **Cutting a trailer/editing video in Premiere (KATANA).** The actual timeline mutation only exists inside Premiere's UXP host process on this machine. No amount of cloud brain work substitutes for it — brain-side work can produce the *plan*, but applying it needs Premiere open, here.
- **Full computer control** (the tier Brandon explicitly chose) — by definition anything that drives other native apps, the file system as seen by this OS, or hardware is local-only; no brain-side equivalent exists.
- **Quill, as currently built** — its data (drafts, library) lives in browser IndexedDB on this machine and it's a bare dev server; nothing about it is reachable except by being on this box in this browser profile. (This is an artifact of how it happens to be built, not a hard requirement the way KATANA's is — it *could* be redeployed to Vercel with server-side storage like its sibling apps, at which point it would stop being local. But today, it is.)

**Only feel local (already cloud-reachable, or trivially could be):**
- **"Send Pennyworth to email a client."** Drafting/sending email is entirely brain-side already — `/api/eve`'s `draft_client_email` / `send_pending_email` tools exist today in Churlish OS, cloud-hosted, with the RED confirm-gate already enforced server-side. Nothing about this needs the desktop machine at all.
- **"Reach out to a podcast guest — find their channels/contact info, draft/send a message."** Research + drafting is a normal brain/agent task with web access; sending still routes through the same confirm-card law. No local execution required.
- **Churlish OS "local slice."** As detailed in §3, the data and the API are already cloud-side; a desktop view of it is a UI convenience, not new local capability.
- **Social stats / Meta-Facebook ads reporting.** Both are read/report jobs against remote provider APIs (Meta Marketing API, platform analytics) — brain-side work; the desktop hub only needs to *display* the results, same as a dashboard tab would.
- **RLS-OS.** Someone else's cloud-hosted client system; not a local worker on this machine at all, and not part of Brandon's own hub surface.

**The one genuinely two-host fact this inventory confirms:** Brandon's own examples (email vs. trailer) really do split cleanly across the two hosts the task description names — email-type jobs are already fully served by the existing Churlish OS `/api/eve` door and need nothing new locally; video-cutting is the one example that is irreducibly local, and even there, the only real "local worker" that exists today (KATANA) has **no programmatic trigger at all** — it is 100% human-clicks-in-Premiere. Any hub design that wants to "queue" a KATANA job has to either add a queue-polling feature to the KATANA panel itself (new code, not present today) or fall back to OS-level UI automation of Premiere — there is no third option in the current build.
